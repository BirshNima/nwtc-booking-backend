Booking & payment

The funnel already collects and prices the ride. This step adds the money: a Stripe deposit link that goes out only after a person confirms the ride is real — never from the funnel, never with a card field on an NWTC page.

01 The money flow

Two things never happen: the funnel never touches a card, and no charge is created without a human step in between. The customer enters card details only on Stripe's own hosted page, reached by a link dispatch chooses to send.

Funnel submit
6-step funnel builds the payload — service, route, schedule, contact, client-side price
POST /intake · public
Re-prices server-side with verifyQuote(). Writes Customer → Lead → Quote → Booking (idempotent on Reference). Alerts dispatch. No money. Booking = Reserved · Deposit Pending
◆ Human step — dispatch confirms the ride
Driver + vehicle assigned, schedule sane, price checked (especially if flagged as a mismatch). This is the gate.
POST /deposit-link · dispatch only, bearer token
Reads the Booking, computes the deposit from pricing-table.json → deposit, creates a Stripe Checkout Session, writes the link + session id onto the Booking, records a Pending Payment
Confirmation SMS + email
Carries the checkoutUrl. Customer pays on Stripe's hosted page
POST /stripe-webhook · from Stripe, signature-verified
checkout.session.completed → Payment Succeeded, Deposit Paid set, Booking → Deposit Paid, dispatch notified. Ride fully confirmed.
The cash branch

At the review step the customer can choose "cash to the driver" instead of a card. That choice rides in the payload to the Lead and Booking. At the gate, dispatch runs /deposit-link with paymentMethod: "cash" — no Stripe session; the full fare is recorded as a Pending cash Payment and the booking is confirmed (or held for approval over $600 / for a new customer). After the trip the driver runs /record-cash-payment and it becomes Fare Collected. Same human gate, no card.

Why a person in the middle

An instant price is reliable enough to show and to reserve against — but a deposit is money changing hands. Dispatch confirming first catches the impossible pickup time, the address in the wrong county, the SUV request for 8 people, and the rare price bug — before the customer is charged, not after. It costs one tap.

02 The endpoints

All in booking-payment/server.js as framework-agnostic handlers, with adapters for Netlify Functions, Cloudflare Workers, and Express/Vercel at the bottom of the file.

POST

/intake

public · automated

The funnel's submitBooking() posts here. Re-prices, writes the CRM, alerts dispatch. Returns fast; a CRM write failure still 202s and queues an alert with the raw payload so nothing is lost.

Auth
None. Rate-limit at the edge.
Body
The funnel payload (see crm/intake.js header).
Re-price
NWTCPricing.verifyQuote(clientTotal, request, table). On mismatch: the lead is still captured, the client amount is dropped, and the dispatch alert is flagged ⚠ PRICE MISMATCH.
Writes
Customer, Lead, Quote, Booking (reservations), Activity Log — via NWTCIntake.funnelPayloadToCRM(), applied in order, deduped on phone / Reference.
Returns
{ ok, reference, status, amount, priceVerified, records }
POST

/deposit-link

dispatch only · the gate

Called by whoever confirms rides — a button in your ops tool, an Airtable automation, or a manual curl. Requires Authorization: Bearer $DISPATCH_API_TOKEN.

Guard
Booking Status must be Reserved or Confirmed and not already paid. Pass {"force":true} to override; {"depositOverride": 30} to set a custom amount or 0 to waive.
Deposit
NWTCPayments.depositPlan(booking, table) — flat for instant-price rides, percent for custom quotes, none for corporate. See §3.
Cash
{"paymentMethod":"cash"} (or the customer's funnel choice) → no Stripe. Records the full fare as a Pending cash Payment, sets Payment Method: Cash, confirms the booking — unless the fare is over the cash limit or the customer is new, when it goes to Needs Approval and pings dispatch. {"force":true} approves a held one.
Stripe
(card only) One Checkout Session, mode: payment, idempotency key deposit_<Reference>, metadata carries reference / fare / balance / refund window.
Writes
Booking: Deposit Amount, Balance, Deposit Link, Deposit Session Id, Status → Confirmed. Payments: one Pending row.
Returns
{ ok, amount, balanceDue, checkoutUrl, sessionId, expiresAt } for card; { ok, paymentMethod:"cash", held, cashDue } for cash.
POST

/record-cash-payment

dispatch / driver

After a cash trip — the driver (or dispatch) records what was actually collected. Same bearer token as /deposit-link.

Body
{ reference, amount?, type?, gratuity? } — amount defaults to the Booking's Cash Due; type is Balance (default) / Deposit / Gratuity.
Writes
Payments: a Succeeded cash row. Booking: Fare Collected (+=), Fare Collected At, Status → Completed.
Why
Keeps the CRM and the offline-conversion feed (step 6) accurate — a cash fare still counts as revenue for Google Ads bidding.
POST

/stripe-webhook

from Stripe · automated

Signature-verified with STRIPE_WEBHOOK_SECRET. Idempotent — every event id is checked against a Webhook Events ledger before it is handled, and 5xx responses let Stripe retry.

Subscribe
checkout.session.completed, checkout.session.expired, payment_intent.payment_failed, charge.refunded
Raw body
The signature check needs the unparsed body — use the raw-body adapter (express.raw, Netlify rawBodyFor:'stripe').

03 Deposit policy

Lives in pricing/pricing-table.json → "deposit" so you change it in the admin screen, not in code. NWTCPayments.depositPlan() is the one place that reads it.

Ride typeDepositApplied to fare?Refundable
Airport flat / hourly (instant price)$50 flatYes — balance due after the tripUp to 24 h before pickup
Wedding / event / out-of-area (custom quote)25% of the quoted fare
dispatch can override per quote		YesUp to 24 h before pickup
Corporate / on-accountNone — billed per rate agreementn/an/a

Floor: minAmount $25. The deposit is never more than the fare itself. A percent policy with no known fare falls back to the $50 flat so a link can still go out.

Cash ("deposit.cash"): allowed up to maxFare $600. Above that, or for a first-time customer (flagNewCustomers), the booking waits at Needs Approval for dispatch. If you want a card deposit to hold a cash booking's slot, send a normal deposit link instead and tell the customer the balance is cash.

Decision 1 from the launch runbook

These are the recommended defaults ($50 flat / 25% custom / refundable to 24 h). If you want a different number or window, change the four values in pricing-table.json and bump its version — no redeploy of the payment code.

05 What stays manual

Same line as the system blueprint. The payment layer automates collection and reconciliation; it never decides to give money back or to hold a booking hostage.

  • Refunds human — you issue them from the Stripe dashboard. NWTCPayments.isRefundable(pickupISO, plan) tells you if the ride is still inside its 24 h window; the choice is yours. The webhook only records what you did.
  • Cancellations inside the window human — fee or goodwill waiver is a judgement call.
  • Deposit overrides & waivers human — passed explicitly on /deposit-link; never automatic.
  • Releasing a held booking human — after a payment failure, dispatch decides.
  • Approving a cash booking human — every one is confirmed by dispatch; large fares and new customers are held explicitly. Recording the collected cash is a one-line call the driver makes after the trip.
  • Corporate billing human — on-account, invoiced per agreement, outside this flow.

06 Deploy & test

  1. Copy config.example.env → .env. Fill Stripe test keys, the Airtable token + base id, a DISPATCH_API_TOKEN (64 random chars), and a DISPATCH_WEBHOOK_URL (a Make catch-hook or Slack incoming webhook).
  2. Add two tables to the Airtable base: Webhook Events (Event Id, Received) and confirm Payments has Amount / Type / Method / Processor Ref / Status / Note. Booking needs the deposit fields the server writes (Deposit Amount, Balance, Deposit Link, Deposit Session Id, Deposit Paid, Deposit Paid At) plus the cash fields (Payment Method, Payment Preference, Cash Due, Fare Collected, Fare Collected At) and a Needs Approval option on Status.
  3. Deploy the three handlers. In Stripe → Developers → Webhooks, add the endpoint and subscribe to the four events; paste the signing secret into .env.
  4. Set window.NWTC_INTAKE_ENDPOINT on the funnel page to the deployed /intake URL. Submit one airport booking — confirm one Lead, one Customer, one Booking (Reserved), and a dispatch alert.
  5. Confirm that booking, then curl -H "Authorization: Bearer <token>" -d '{"reference":"NWTC-…"}' …/deposit-link. Open the returned checkoutUrl.
  6. Pay with Stripe test card 4242 4242 4242 4242, any future expiry, any CVC. Confirm Payment → Succeeded, Booking → Deposit Paid, Balance correct, dispatch notified.
  7. Test the sad paths: card 4000 0000 0000 9995 (declined) → Payment Failed; let a session expire → checkout.session.expired handled. Use the Stripe CLI (stripe listen --forward-to …/stripe-webhook) to replay events locally.
  8. Test cash: submit a funnel booking with "cash to the driver" selected. Confirm the Lead/Booking show Payment Preference: cash, then POST /deposit-link {"reference":"…","paymentMethod":"cash"} → no Stripe, Booking Confirmed, a Pending cash Payment for the full fare, cash confirmation sent. Then POST /record-cash-payment {"reference":"…"} → Payment Succeeded, Fare Collected set. Try a fare over $600 → Needs Approval + dispatch alert.
  9. Re-submit the same funnel payload twice — verify still one Lead, one Booking (idempotent on Reference).
  10. Only when all eight pass: swap to Stripe live keys and a live webhook secret.
PCI

Card data never reaches NWTC servers — Checkout is hosted by Stripe — so you stay in the simplest SAQ-A scope. Do not add card fields to the funnel or anywhere else. That is the whole reason the link goes out after confirmation instead of a checkout living in the funnel.
